Seal

A proven checkpoint for AI agents: no exact human approval, no action. And a record you can check yourself.

Seal sits at the MCP tool boundary, where model output becomes a real external effect. It mediates the action, records the decision, and leaves a receipt a skeptic can rerun.

by velvetmonkey · private product-family hub · claims need receipts.

AI agents are crossing the line from suggestion into action. They can send money, delete data, update tickets, call vendors, and trigger production systems through MCP tools.

That power is useful. It is also where a hallucination, prompt injection, stale approval, or confused workflow becomes a real-world effect. Seal answers at the point of effect: did a human approve this exact request?

How it works

  • Mediate every guarded action. A guarded MCP tool call forwards only when its target commitment has a live human approval.
  • Record every decision. Allowed and blocked decisions produce receipts and tamper-evident record-chain evidence.
  • Prove the rulebook. The kernel rules are machine-checked theorems in Lean 4.
  • Check every body that runs it. The Rust host, browser wasm, and JavaScript checkers are byte-conformance-tested against the proven rulebook over a corpus; they are not themselves proved bug-free.

What's proven

  • Four-gate non-bypass. A guarded call that reaches the deployed step core cannot route forward without satisfying the mediation gates.
  • Append-only, tamper-evident record. Decision logs are modeled as hash chains whose heads change on append and expose tampering under the stated hash-step assumptions.
  • Unconditional capability adequacy. A held approval authorizes only its exact target for all runtime inputs, modulo the named SHA-256 collision-resistance assumption A-CR.
  • Single-request non-interference. For one request, the observable decision and record depend on the relevant authorization view, not unrelated protected state.
  • Cross-session replay isolation. Replay state is scoped so one session's replay bookkeeping does not silently authorize another session.

Axiom footprint: {propext, Classical.choice, Quot.sound}. How to cash the receipt: run lake build and lake exe axiom_check in the Lean repos, then run the conformance bridge in seal-host. The bridge checks model == native == wasm == deployed == JS over the corpus.

Honest boundaries

- Seal proves properties of the mediation KERNEL, not of the whole deployed system.
- Seal does NOT prove SHA-256 collision resistance in Lean; it is a named, scoped cryptographic assumption (A-CR).
- The deployed Rust / wasm / JS are NOT proven bug-free; they are tied to the proof by byte-exact conformance testing over a corpus, not for every possible input.
- Seal guarantees AUTHORIZATION match, not INTENT match: if a human approves a malicious-but-valid request, Seal will execute it.
- Seal does NOT prevent compromise of hosts, browsers, build systems, keys, operators, or downstream tools.
- Seal's audit chain is tamper-EVIDENT, not tamper-IMPOSSIBLE.
- Seal does NOT make the AI smarter or prevent hallucinations; it stops an unapproved effect.
- Axiom footprint {propext, Classical.choice, Quot.sound} is the minimal classical fragment; no extra axioms.
